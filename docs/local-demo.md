# Running and demoing edops on your PC

Everything runs locally: seven Docker containers (Postgres, RabbitMQ, the API, the relay, two
workers, the orchestrator) plus the test suite. All commands are for **Windows PowerShell**, run
from the project folder. Every command here was run on this machine before being written down.

Prefer clicking to typing? [demo-ui.md](demo-ui.md) is the same demo using Swagger, Adminer,
the RabbitMQ dashboard, Docker Desktop and the VS Code Testing panel.

## 1. One-time setup
You need **Docker Desktop**, **Python 3.12**, and **Git**.

```powershell
cd "C:\Web dev\edops"
copy .env.example .env
py -3.12 -m venv C:\webdev\venvs\edops
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned   # once per user, lets the venv activate
& C:\webdev\venvs\edops\Scripts\Activate.ps1
pip install -r requirements-dev.txt
```

After activation the prompt starts with `(edops)`. Every new terminal needs the `Activate.ps1`
line again (or select that interpreter in VS Code so its terminals activate it for you).

## 2. Start the stack
Start **Docker Desktop** first and wait until it says it is running. Then:

```powershell
cd "C:\Web dev\edops"
& C:\webdev\venvs\edops\Scripts\Activate.ps1
docker compose up -d --build --wait
docker compose ps
```

Expected: eight rows, all `Up ... (healthy)`: the seven services `inventory-worker`,
`orchestrator`, `order-api`, `outbox-relay`, `payment-worker`, `postgres`, `rabbitmq`, plus
`adminer`, a database UI used by the click-through demo.

Quick check: `Invoke-RestMethod http://localhost:8000/health` prints `status: ok`.

Useful pages while it runs:
- API docs (auto-generated by FastAPI): http://localhost:8000/docs
- RabbitMQ dashboard: http://localhost:15672 (user `edops`, password `edops`). The **Queues**
  tab shows `payment`, `inventory` and `orchestrator`.

## 3. Run the tests
```powershell
ruff check .
pytest -v
```
Expected: `All checks passed!` and `46 passed` in about a minute. The tests use their own
database (`edops_test`) and their own RabbitMQ queues, so they never touch the running demo's
data. Run them once before a presentation; the first run also warms Docker up.

The same suite runs on every push in GitHub Actions (repo → **Actions** tab). A green run there
is proof the guarantees hold on a clean Linux machine, not only on this PC.

## 4. The demo (about 10 minutes)
Run these in order **in one PowerShell window**: later steps reuse variables (`$api`, `$oid`)
set by earlier ones. Each step has a line to say while it runs.

### Step 0: setup for the session
```powershell
cd "C:\Web dev\edops"
& C:\webdev\venvs\edops\Scripts\Activate.ps1
$api = "http://localhost:8000"
docker compose ps
```
> *"Seven processes: Postgres is the source of truth, RabbitMQ only carries events, and five
> app processes. Only the relay ever publishes to the broker."*

### Step 1: one order, sent twice (API idempotency)
```powershell
$key  = "demo-" + [guid]::NewGuid()
$body = '{"customer_id":"c-demo","amount_cents":1999,"items":[{"sku":"SKU-1","quantity":1}]}'
$first  = Invoke-RestMethod -Method Post -Uri "$api/orders" -Headers @{ "Idempotency-Key" = $key } -ContentType "application/json" -Body $body
$second = Invoke-RestMethod -Method Post -Uri "$api/orders" -Headers @{ "Idempotency-Key" = $key } -ContentType "application/json" -Body $body
"first=$($first.order_id)  second=$($second.order_id)"
$oid = $first.order_id
Invoke-RestMethod "$api/orders/$oid" | Format-List order_id, status, saga_step, charges, refunds
```
Expected: the **same order id twice**, then `status: CONFIRMED`, `charges: 1`, `refunds: 0`.
(If it still says `PENDING`, run the last line again a second later.)

> *"A client retry with the same Idempotency-Key gets the original response back. It never
> creates a second order."*

Optional: the same key with a different body is refused, and no key is refused too.
```powershell
$other = '{"customer_id":"c-demo","amount_cents":5000,"items":[{"sku":"SKU-1","quantity":1}]}'
try { Invoke-RestMethod -Method Post -Uri "$api/orders" -Headers @{ "Idempotency-Key" = $key } -ContentType "application/json" -Body $other } catch { "same key, different body -> " + $_.Exception.Response.StatusCode.value__ }
try { Invoke-RestMethod -Method Post -Uri "$api/orders" -ContentType "application/json" -Body $body } catch { "no key -> " + $_.Exception.Response.StatusCode.value__ }
```
Expected: `-> 409`, then `-> 400`.

### Step 2: the broker redelivers (consumer idempotency, the core question)
Mark the order's `OrderCreated` event as unpublished, so the relay sends the **same message**
again, exactly what a broker redelivery looks like to the payment worker:
```powershell
docker compose exec -T postgres psql -U edops -d edops -c "UPDATE outbox SET published_at = NULL WHERE aggregate_id = '$oid' AND event_type = 'OrderCreated' RETURNING message_id;"
docker compose logs --no-log-prefix payment-worker | Select-String "duplicate OrderCreated" | Select-Object -Last 1
"charges now: " + (Invoke-RestMethod "$api/orders/$oid").charges
```
Expected: `UPDATE 1`, then a log line with `"msg": "duplicate OrderCreated skipped message_id=..."`
(same id the UPDATE printed), then `charges now: 1`. If the log line is not there yet, run the
second command again after a second.

> *"The worker records the message id in the same database transaction as the charge, and acks
> only after commit. A redelivered message finds its id already recorded and is skipped. Under
> that, a UNIQUE constraint makes a second charge impossible at the database level."*

### Step 3: a failure after stock was reserved (compensation)
The customer id `fault-after-reserve` makes the orchestrator reject the order after stock is
held, which forces the release-and-refund path:
```powershell
$key2 = "demo-" + [guid]::NewGuid()
$comp = Invoke-RestMethod -Method Post -Uri "$api/orders" -Headers @{ "Idempotency-Key" = $key2 } -ContentType "application/json" -Body '{"customer_id":"fault-after-reserve","amount_cents":1999,"items":[{"sku":"SKU-2","quantity":1}]}'
Invoke-RestMethod "$api/orders/$($comp.order_id)" | Format-List status, saga_step, charges, refunds
docker compose exec -T postgres psql -U edops -d edops -c "SELECT sku, quantity, status FROM reservations WHERE order_id = '$($comp.order_id)';"
```
Expected (run the middle line again if it is not finished yet): `status: FAILED`,
`saga_step: COMPENSATED`, `charges: 1`, `refunds: 1`, and the reservation row is `released`.

> *"The orchestrator owns the flow: payment, then stock. When something fails after both, it
> releases the stock, then refunds, each exactly once. Both compensations are idempotent by
> database state."*

Other failure ids to try the same way: `fault-payment-declined` (FAILED, no charge) and
`fault-stock-rejected` (COMPENSATED, one charge and one refund).

### Step 4: rebuild one order's path from logs alone
```powershell
docker compose logs --no-log-prefix order-api outbox-relay payment-worker inventory-worker orchestrator |
  Select-String $oid |
  ForEach-Object { $_.Line | ConvertFrom-Json } |
  Sort-Object ts |
  Format-Table logger, msg, correlation_id -AutoSize
```
Expected: about 25 lines, from `order created` through `published OrderCreated`,
`charged 1999 cents`, `PAYMENT_REQUESTED -> STOCK_REQUESTED`, `reserved`,
`STOCK_REQUESTED -> CONFIRMED`, and the `duplicate OrderCreated skipped` from step 2, all with
the same correlation id. (Lines from different containers can appear a millisecond out of
order.)

> *"Every log line is JSON with order_id and correlation_id, and the correlation id travels
> inside every event, so one order's whole path comes back from a single filter."*

### Step 5: kill a worker at the worst moment (chaos test)
```powershell
pytest tests/test_chaos.py -v
```
Expected: `1 passed` in about 6 seconds.

> *"This starts its own copy of every process, freezes the payment worker right after it
> committed the charge but before it acked, kills it, and starts a new one. The broker
> redelivers, the dedupe stops it, and the order still finishes with exactly one charge. The
> test was shown failing against a deliberately broken dedupe, so it can actually catch the bug."*

### Step 6: restart the database under the running system
```powershell
docker compose restart postgres
$key3 = "demo-" + [guid]::NewGuid()
$r = Invoke-RestMethod -Method Post -Uri "$api/orders" -Headers @{ "Idempotency-Key" = $key3 } -ContentType "application/json" -Body $body
Invoke-RestMethod "$api/orders/$($r.order_id)" | Format-List status, charges
docker compose logs --no-log-prefix --since 2m payment-worker | Select-String "connection lost|payment started" | ForEach-Object { ($_.Line | ConvertFrom-Json).msg }
```
Expected: the order reaches `CONFIRMED` with `charges: 1` (wait a few seconds and repeat the
`Format-List` line if it is still `PENDING`), and the worker log shows
`database connection lost, exiting` followed by `payment started`.

> *"A worker whose database connection dies exits on purpose, and Docker restarts it. I found
> this while writing the failure catalog: before the fix, workers retried one message about
> 1,200 times a second forever while reporting healthy."*

### Step 7: the one-command proof, and where the evidence lives
```powershell
python scripts/smoke.py $api
```
Expected last line: `RESULT: PASS, one order and exactly one charge`.

Then show:
- `docs/design.md` section 2 (state machine), section 3 (failure catalog, including the entries
  marked **handled badly**), and section 7 (which test proves each invariant).
- The green run in the GitHub **Actions** tab.

> *"What it does not handle, on purpose: a message that always fails is retried forever, with
> no backoff and no dead-letter queue. That is documented as handled badly, and it is the first
> item of future work."*

## 5. Stop and reset
```powershell
docker compose down          # stop; keeps the data
docker compose up -d --wait  # start again with the same data
```
For a clean slate before a presentation (fresh database, stock back to SKU-1: 10, SKU-2: 5):
```powershell
docker compose down -v
docker compose up -d --build --wait
```
`-v` deletes the database volume. Use it after any change to `db/init.sql` too, because that
file only runs when the volume is first created.

## 6. Troubleshooting
| Symptom | Fix |
|---|---|
| `ruff` / `pytest` "is not recognized" | The venv is not active in this window: `& C:\webdev\venvs\edops\Scripts\Activate.ps1` |
| `Activate.ps1 cannot be loaded because running scripts is disabled` | `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`, then open a new terminal |
| `error during connect ... dockerDesktopLinuxEngine` | Docker Desktop is not running; start it and wait until it is ready |
| `pytest` exits with "Postgres unreachable" or "RabbitMQ unreachable" | The stack is not up: `docker compose up -d --wait` |
| `ACCESS_REFUSED` in a worker log | `.env` RabbitMQ user/password changed after RabbitMQ was created: `docker compose up -d --force-recreate rabbitmq`, then restart the workers with `docker compose restart` |
| Port 8000, 5432 or 5672 "already in use" | Another program (or a local Postgres/uvicorn) holds it; stop it, or stop the other copy of the stack |
| An order stays `PENDING` | `docker compose ps`: every service must be healthy. Then check that service's log, e.g. `docker compose logs --tail 30 payment-worker` |
| `curl` in PowerShell shows a "Security Warning" prompt | PowerShell's `curl` is an alias for `Invoke-WebRequest`. Use `Invoke-RestMethod` as above, or `curl.exe` |
